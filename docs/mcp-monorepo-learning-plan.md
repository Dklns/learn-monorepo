## 2. 已确认的第一阶段目标

从“听过并理解部分用途”走到“能解释取舍，并独立组织一个小型 workspace”。

建议用两个小型 React 应用和一个共享 TypeScript 包贯穿学习。第一阶段优先共享纯逻辑，而不是立刻搭组件库，以减少 React peerDependencies、样式打包等旁支干扰。

完成时应能：

1. 画出多仓库和 monorepo 两种布局，解释仓库、应用、包、版本、部署之间的区别。
2. 根据共享改动频率、团队边界及发布节奏，给出一次是否采用 monorepo 的理由；不能只回答“复用代码更方便”。
3. 在允许查官方文档、但不由教师逐步代写的条件下，组织两个应用与一个共享包，声明并使用本地 workspace 依赖。
4. 修改共享包后说明两个应用为什么受到影响，完成针对性的验证，并解释是否需要重新构建或部署。

以上为第一阶段的学习检验标准，不是已经掌握的能力。接受目标不等于已完成实践；实操时按步骤推进，不在连接准备阶段自动搭建项目。

## 4. 首课概念图

### 方案 A：多个仓库，共享代码通过版本消费

```text
公共代码仓库 ── 版本 v1 ──→ 应用 A 仓库 ──→ 部署 A
             └─ 版本 v1 ──→ 应用 B 仓库 ──→ 部署 B

修复公共代码 → 形成新版本／新引用 → 消费方更新 → 验证 → 各自部署
```

用户提出的 tag 方案属于这个方向。具体通过 Git 依赖还是发布包消费尚未说明；两者不等同。此处 tag 是版本定位手段，不把它自动等同于包发布，也不假设普通 tag 永不可改动。

### 方案 B：一个仓库，多个项目共同开发

```text
一个 Git 仓库
├── apps/a ───┐
├── apps/b ───┤── 声明依赖 ──→ packages/shared
└── packages/shared

部署 A 与部署 B 仍可分别进行；对外发布的包也可以保留独立版本。
```

- 配置本地 workspace 依赖后，部分内部联调可以不经过“先发布包、再更新消费方版本”的流程。
- 同仓支持把共享实现和调用方调整放入同一次提交，但仍要验证兼容性与影响范围。
- 同一次提交不等于多个线上系统原子部署；源码改变不等于已部署应用自动更新。
- 相似代码不一定应该抽到一起：业务含义不同或变化方向不同，过早共享可能增加耦合。
- Monorepo 不自动解决权限、循环依赖、边界约束或构建性能问题；工具与规则仍然需要设计。

## 5. 教学方法

每个概念采用“问题背景 → 对比图 → 一句话解释 → 用户复述／迁移小题 → 必要时动手”。每次聚焦一个关键问题，不在一个回合堆砌所有工具。

- 优先复用用户熟悉的 TS/React 与 pnpm 语境，不重教基础语法和常用 Git 按钮操作。
- 锁文件基础仅快速校准；理解其作用不等于已掌握 CI 中的 frozen lockfile、跨平台差异或工具链一致性。
- 把路由首屏动态引入经历当作依赖关系的类比入口，但明确模块加载图、包依赖图和任务执行图不是同一张图。
- 用户先解释选择，教师再补充遗漏；不把工具命令背诵当作学习完成标准。
- 已表现出理解的内容可跳过；遇到包边界或构建前置知识缺口时插入小补课。
- 实操前才确认 Node/pnpm 版本和运行环境，不为建画像扫描整台设备或修改业务代码。

## 6. 暂缓内容与后续分流

暂不把 Nx、Turborepo、Bazel、远程缓存或复杂发布平台设为前置课程。第一阶段用 pnpm workspace 解释基础问题；遇到任务重复或构建成本问题后再判断是否需要任务编排工具。

第一阶段复盘后再选择：

- 理解够用：停在架构判断与日常使用，整理速查图。

- 架构迁移：在具体项目需求出现后，讨论迁移步骤、权限、团队协作与回退。
