## 1. 问题背景

第 8 课你改 shared 之后，靠人脑记住了"要重建 shared，A、B 都受影响"。
当前仓库只有三个包，人脑够用。但如果包有 20 个、依赖链三层深，
每次变更都靠人判断"该重建谁、按什么顺序"，迟早出错。

本单元回答：**机器怎么知道构建顺序和影响范围？不重复构建的缓存怎么做？**
本课先用 pnpm 自带能力解决"顺序"和"范围"，缓存问题留给下一课的 Turborepo。

## 2. 概念图：从一张图到另一张图

```text
你熟悉的模块加载图（第 1 阶段提过）：import 谁 → 加载谁

任务执行图（本课新主角）：
  packages/shared（无本地依赖）
     ↑ 被依赖
  apps/a、apps/b（依赖 shared）

拓扑顺序：被依赖者先构建。
  pnpm -r run build → 自动按拓扑序：shared 先，a、b 后
```

要点：**任务图由 package.json 的依赖声明推导**，不需要你在任何地方手写顺序。
这正是第 2 课"谁用谁声明"的又一次回报：声明不只为了安装，还是任务图的输入。

## 3. 预测题（只作答，先不执行）

1. 在仓库根目录跑 `pnpm -r run build`，三个包的构建顺序是什么？
   依据是什么机制？
2. 你改了 shared 之后，想"只重建 shared 以及所有依赖它的包"，不动无关项目。
   不查文档，先给出你猜想的命令形态或思路（猜错无妨）。
3. 假设 shared、A、B 都刚构建过，什么都没改，再跑一遍全量构建：
   你觉得哪些时间被浪费了？pnpm 现有机制能避免吗？

## 4. 动手（预测点评后进行）

1. 根目录全量构建：`pnpm -r run build`，观察输出里的顺序；
2. 定向重建：`pnpm -r --filter ...@learn/shared run build`，
   观察这次构建了哪些包、顺序如何；
3. 对照实验：`pnpm -r --filter @learn/shared... run build`，
   记录两种选择器（`...@learn/shared` 与 `@learn/shared...`）构建范围的差别；
4. 全量重跑一遍 `pnpm -r run build`，用秒表或输出时间感受"什么都没改却全部重来"的成本；
5. 思考题（不动手）：如果 shared 的 src 一个字没变，但 dist 被人删了，
   第 2 步的命令能恢复它吗？依据是什么？

## 5. 本课要点

- 拓扑序构建：`-r` 递归执行时 pnpm 自动按依赖图排序，无需手写顺序。
- 选择器语法：`...pkg` = pkg 及其依赖者（dependents）；`pkg...` = pkg 及其依赖（dependencies）。
  改共享包后重建影响范围用前者。
- pnpm 能解决"顺序"和"范围"，但解决不了"没变就跳过"——每次都真实执行，
  这是 Turborepo（任务图 + 内容哈希 + 缓存）要补的洞。

### 教师判定

## 9. 实验结果与结课（2026-09-20）

### 用户报告

- `pnpm -r run build`：构建 shared、A、B，耗时 0.9s。
- `pnpm -r --filter ...@learn/shared run build`：构建 shared、A、B，耗时 0.8s。
- `pnpm -r --filter @learn/shared... run build`：仅构建 shared，很快。
- 重复全量构建结果相同。
- 思考题（dist 被删能否恢复）：能，因为该命令就是为 shared 及其依赖者构建产物。

### 教学判定

- 两个选择器方向均验证正确：`...shared` = shared + 依赖者（A、B）；`shared...` = 仅 shared（无本地依赖）。
- 教师补充：任务图里只出现 workspace 内的包；zod 是外部依赖，不进入任务图。
- 思考题正确。补充：这说明 dist 是可再生的派生产物，src 才是事实源——也是 dist 可以进 .gitignore 的原因。
- 全量重跑结果相同印证题 3 结论：pnpm 无缓存，未变更也全部真实执行；0.9s 在玩具仓库无所谓，放大到真实项目即分钟级浪费。Turborepo 由下一课展开。

## 10. 拓扑序补讲与迁移小题（2026-09-21）

- 用户反馈“还是不清楚拓扑序构建”，教师补讲：拓扑序 = 不违反依赖关系的排队方式；用 socks/shoes 类比 + 本仓库依赖图展开。
- 迁移小题（core/utils/ui/admin 四包图）用户全对：合法顺序、可并行集合、失败不传染其依赖。
- 教师精化：①并行是分波次的——首波 core+utils，core 完成后 ui 可与 utils 并行；②失败传染方向规则：失败沿“被谁依赖”方向向消费方传染，不向它依赖的包传染（本例无人依赖 admin，故不扩散）；CI 含义：任一失败都阻塞合并。
- 记录：本轮为纯概念补讲，未动工程文件；CI 单元预测题仍未提交。
