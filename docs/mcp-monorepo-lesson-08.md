## 1. 先预测，再动手

当前状态：packages/shared/src/index.ts 里的 formatPrice 会把数字格式化为两位小数字符串。两个应用都通过包名 @dklns/shared 调用它，页面显示 12.30 和 99.90。

假设你现在把 formatPrice 的行为改掉（例如改成三位小数，或加上货币符号）。请先只回答，不执行命令：

1. 从你保存这个文件开始，到 http://localhost:5173 的页面上出现新结果，中间要经过哪些步骤？哪些必须重新执行，哪些不需要？
2. 如果只启动了 A 的开发服务器，B 的服务器没开。B 下次启动时会拿到新结果还是旧结果？为什么？
3. 真实上线时，这条链路里还缺哪一环？（提示：本机页面能跑通，不等于用户能看到）

预测写错也有价值：先写下来，再用实验结果对照。不要先跑命令再倒推答案。

## 2. 动手实验

预测写完后按顺序执行，每一步都留意现象。

### 第 1 步：改共享包源码

打开 packages/shared/src/index.ts，只改 formatPrice 的行为，例如：

```ts
export function formatPrice(amount: number): string {
  return amount.toFixed(3);
}
```

不要改动两个应用里的任何代码。

### 第 2 步：先看页面，不要先构建

回到浏览器看 A（http://localhost:5173）和 B（http://localhost:5174）。如果服务器已经关掉，先重新启动再看。

记录：页面显示变了吗？如果没变，如实记下“没变”，不要马上去改配置。

### 第 3 步：重新构建共享包

在仓库根目录执行：

```bash
pnpm --filter @dklns/shared run build
```

### 第 4 步：再看页面

如果显示仍未变化，依次尝试并记录到哪一步才生效：

1. 刷新页面（Windows 下 Ctrl+F5 强制刷新）。
2. 重启对应的开发服务器（终端里 Ctrl+C 停掉，再重新运行启动命令）。
3. 重启后再刷新页面。

### 第 5 步（可选，验证生产构建）

```bash
pnpm --filter "@dklns/app-*" run build
```

观察构建是否仍然成功。这一步说明应用自身的构建产物需要重新生成，和开发服务器的行为是两件事。

## 3. 值得记住的三个点

- 共享包以 dist 产物被消费时，改源码本身不会自动进入应用，必须先重新构建共享包。
- 开发服务器有没有自动感知变化，取决于它消费的是源码还是产物文件；这类行为要用实验确认，不能凭印象断言。
- 应用自己也要重新构建并部署：开发服务器能跑，不等于线上用户拿到了新结果。

## 7. 用户预测（原话记录）

主问题：保存文件开始后，需要重新构建 shared 的产物，然后强制重新安装 A B 的依赖，不需要修改 A B 的源代码，因为导入和使用方式没有改变，并且热更新，不需要重新开始本地服务。

## 8. 预测点评与观察要点

| 用户判断 | 评价 | 说明 |
| --- | --- | --- |
| 重新构建 shared 产物 | 正确 | exports 指向 dist/index.js，应用消费的是产物而不是 src 源码 |
| 强制重新安装 A、B 的依赖 | 不必要 | workspace 协议下 node_modules 里是一条指向 packages/shared 的链接，文件内容变化不改变这条依赖关系；只有依赖声明本身变化（增删依赖、改协议范围、改包名）才需要重新安装 |
| 不需要修改 A、B 源代码 | 正确 | 导入名、参数与返回类型都没变，公共接口不变，消费方代码不用动；若返回类型改变，TypeScript 会先报错，那时才必须改消费方 |
| 热更新，不需要重启本地服务 | 待实验确认 | “不需要重启服务”这一半很可能成立，但原因不是 React 组件式的热更新，而是开发服务器是否监听到产物文件变化；以实际观察为准 |
| 追问 1：新结果 | 正确 | 前提是 shared 已重新构建；未重建时 B 拿到的仍是旧结果 |
| 追问 2：重新构建 A、B 产物 | 正确但不完整 | 重建之后还要把新产物部署，用户端才会变；A、B 的构建与部署彼此独立 |

### 观察要点（把“热更新”从印象变成证据）

1. 改完 src、还没有重新构建 shared 时，页面应无变化。这一步排除“改源码直接生效”的猜想。
2. 重新构建 shared 后先不要手动刷新，观察浏览器表现：自动刷新、必须手动刷新，还是必须重启服务？逐条记录。
3. 想要硬证据：开发者工具 → Network → 找到来自 @dklns/shared 的模块请求 → 看返回内容是 toFixed(2) 还是 toFixed(3)。这比只看页面数字更可靠。
4. 若 B 的服务器一直没开，按追问 1 重启 B，验证是否显示 99.900。

### 教师实际文件核对

### 教学判定

- 三步现象与观察要点预期一致：改源码不构建页面不变；重建 shared 后开发服务器感知产物文件变化并自动刷新；最终值符合预期。
- “自动刷新”的原因不是用户最初预测的“依赖热更新”，而是 Vite 开发服务器监听了它所服务模块对应的文件（经由 workspace 链接指向 shared/dist），产物文件被重建触发更新推送；属于文件监听行为，不依赖 node_modules 重装。
- 第 5 步生产构建已完成：A、B 产物文件名哈希由 index-D6vGkNbY.js / index-BWH_wvvs.js 变为 index-BFMAn0E3.js / index-BWNdEQl5.js，印证“内容变则产物变”，部署交付的正是这批新文件。
- 浏览器显示值为用户报告，教师未查看浏览器；以源码与产物内容为准。
- 本课实验完成；下一步为变更链路复盘，检验路线第一阶段第 2、4 条目标。

## 10. 收官复盘作答（2026-09-20）

### 用户回答（原话）

1. “先修改 packages/shared/src/index.ts，然后构建 shared 的产物，再构建 A B 的产物，最后部署上线”
2. “因为 A B 都通过 workspace 指向了 shared 的 dist 并且 A B 都引用了被修改的函数。当修改 shared 的内容并没有被 A 使用时，A 不会受到影响”
3. “monorepo 方案省掉了推送 shared 然后给 shared 打 tag，修改 A B 的 package.json 中依赖的版本”

### 教师判定与补充

| 题 | 判定 | 说明 |
| --- | --- | --- |
| 1 链路复述 | 基本正确，缺标注 | 顺序完整；但未按题意标注各步实际状态：前三步已实际执行，“部署上线”尚未发生，dist 仅在本机磁盘。另需区分：开发预览靠文件监听无需构建应用；“构建 A、B 产物”属于上线链路，两条链路不同 |
| 2 影响边界 | 正确 | 抓住“被引用才受影响”的核心。教师补充：影响范围由消费方模块图（import 可达路径）决定；还可区分“产物不变”（新增 A 未引用的导出）与“产物变但行为不变”（实现微调、可观察结果相同）两个层次 |
| 3 选型理由 | 部分正确 | 省掉版本往返（发布/打 tag → 改消费方版本 → 重装）具体正确，且指出同仓可同次提交共享改动与消费方调整；但题目明确要求说代价，只答了收益半边，待补充 |

### 教师判定

- 诚实承认未知，符合记录规则；不把空白推断为能力不足。
- 代价半边已给出三项：clone 成本、CI 配置负担、协作冲突风险；记为初步证据。CI 一项需校准：monorepo 的 CI 可以统一配置，难点在于只跑受影响项目、避免全量构建，不是“必须分别配置”。
- 兼容性责任与回退方式两项由教师补充讲解（见下），记为待实践巩固的新知识，不记为已掌握。

### 教师补充：兼容性责任与回退

- 版本边界消失后，验证责任落在改动方：改 shared 的人必须在合并前验证所有消费方（workspace 级类型检查、运行 A、B 的测试/构建）；这取代了独立仓库中“发布新版本后由消费方自行决定何时升级”的缓冲。
- 回退：workspace:* 没有旧版本可退，只能回滚代码（如 git revert 或恢复旧实现），且一旦合入，所有消费方同时面对变化；独立仓库方案中消费方可停留在旧版本。
- 由此产生的不适合场景示例：需要独立开源/外部消费的包、权限边界不同的团队、发布节奏差异极大且互相不信任变更的项目。
