# 第 12 课（第二阶段·单元 2 续）：缓存与增量——Turborepo 补上"没变就跳过"

日期：2026-09-20
前课：docs/mcp-monorepo-lesson-11.md
状态：预测已提交并点评；等待用户执行第 4 节动手（安装 turbo、写 turbo.json、体验 MISS/HIT）。

## 1. 问题背景

上一课的结论：pnpm 能排序（拓扑序）、能选范围（选择器），但每次构建都真实执行。
全量 0.9s 的玩具仓库无所谓，真实项目是分钟级。本课引入 Turborepo，
只回答一个问题：**它怎么知道"输入没变，直接复用上次结果"？**

## 2. 概念图：构建的输入与输出

```text
一次构建 = f(输入) → 输出

输入（Turborepo 对其做内容哈希）：
  ├── 包内源码文件内容
  ├── 依赖的版本与锁文件
  ├── 构建配置（tsconfig、vite.config 等）
  └── 它依赖的本地包的构建结果（任务图，继承自 pnpm workspace）
输出：
  └── dist（turbo.json 里声明的 outputs）

同一份输入 → 必然同一份输出 → 上次的结果可以直接复用（缓存命中）
```

要点：Turborepo 不是"判断文件改没改"，是"对输入做哈希，哈希没见过才真构建"。
所以它能跨分支、甚至跨机器（远程缓存）复用。

## 3. 预测题（只作答，先不执行）

1. Turborepo 怎么判断"shared 没变，不用重建"？它需要记录哪些信息？
2. 缓存命中时，A 的 dist 是从哪来的？如果你手动删掉 `.turbo` 缓存目录再构建，
   会发生什么？
3. 除了源码内容，还有哪些东西变了就必须重新构建？能想到几类算几类。

## 4. 动手（预测点评后进行，命令以点评后的版本为准）

1. 根目录安装 Turborepo 为开发依赖：`pnpm add -D turbo -w`（-w 表示装在 workspace 根）；
2. 根目录新建 `turbo.json`，声明 build 任务：依赖关系 ^build（先建依赖的包）、
   outputs 为各包的 dist；
3. 用 `pnpm turbo build` 跑第一次（全部 MISS，真实构建并写入缓存）；
4. 不改任何文件，立刻再跑一次，观察 HIT 与耗时对比；
5. 改 shared 的 src 一个字符，重跑：观察哪些包 MISS、哪些 HIT；
6. 手动删掉 packages/shared/dist，再跑 `pnpm turbo build`：dist 回来了吗？
   这次是真构建还是缓存恢复？

## 5. 本课要点（先留白，实验后回填）

- 缓存命中与否由输入哈希决定，不由文件时间戳或"改没改"决定。
- outputs 声明是缓存复用的前提：没声明产物路径，命中了也无物可复用。
- 任务图仍来自 workspace 依赖声明；Turborepo 复用而非取代 pnpm 的拓扑关系。

## 7. 预测题作答与点评（2026-09-20）

### 用户回答（原话）

1. “需要记录 shared 的源码文件是否发生过改变，依赖的版本是否发生改变”
2. “从原来的 dist 来。重新构建”
3. “各依赖的版本发生改变，各种配置文件发生改变”

### 教师判定

| 题 | 判定 | 说明 |
| --- | --- | --- |
| 1 | 方向对，模型需校准 | 抓住了源码与依赖版本两类输入；但 Turborepo 不做“是否改变”的差量对比，而是对全部输入做内容哈希、与缓存库中的哈希比对——“改没改”是哈希碰撞的推论，不是记录的状态 |
| 2 | 半对，需精确 | 缓存命中时 dist 从缓存库（.turbo/cache）恢复，不是从“原来的 dist 目录”来——它和上次产物是两份副本；删缓存目录则未命中、真实重建，这半正确 |
| 3 | 基本正确 | 依赖版本、配置文件都对；教师补充：构建期间读到的环境变量、以及它依赖的本地包的哈希（任务图继承）也在输入内 |

- 关键概念校准：“差量比对”与“内容哈希”是两种模型，后者是跨分支、跨机器（远程缓存）复用的前提。
- 记录性质：题为预测；哈希模型与缓存恢复由实验验证。
